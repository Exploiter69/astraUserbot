# AstraUserbot — Detailed Job Model

**Status:** Mandatory execution contract  
**Version:** 2.1  
**Scope:** Durable asynchronous work, scheduling, workers, retries, leases, verification, recovery, cancellation, idempotency

## 1. Purpose

An asyncio task is process-local. A durable job is a persisted responsibility Astra has accepted and can explain after restart.

> **Accepted durable work must remain explainable, bounded, recoverable, and auditable across restart, disconnect, cancellation, timeout, and worker failure.**

## 2. Execution Pipeline

```text
TRIGGER
  ↓
VALIDATE
  ↓
AUTHORIZE
  ↓
PLAN
  ↓
PERSIST JOB
  ↓
QUEUE
  ↓
LEASE
  ↓
EXECUTE
  ↓
VERIFY
  ↓
AUDIT
  ↓
REPORT
```

The Job Engine never grants authority. It executes a previously authorized contract.

## 3. Job Types

Initial types:

```text
REMINDER
SCHEDULED_MESSAGE
HTTP_TASK
MEDIA_PROCESS
DOWNLOAD
UPLOAD
INDEX
BACKUP
MAINTENANCE
SYNC
AI_TASK
PLUGIN_TASK
```

A job type defines its payload schema, required capability, retry policy, resource class, idempotency strategy, and verification contract.

## 4. Job Identity

Every job has:

```text
job_id
job_type
created_at
priority
state
payload_ref
scope
idempotency_key (optional)
parent_job_id (optional)
```

IDs are generated by the platform, not by an LLM or untrusted plugin input.

## 5. Payload Contract

Payloads contain bounded intent and references, for example:

```json
{
  "target_chat": "...",
  "message_ref": "...",
  "artifact_ref": "...",
  "options": {}
}
```

They must not contain:

- session strings;
- API keys;
- passwords;
- private keys;
- raw authorization headers;
- arbitrary Python code;
- unlimited shell command strings.

Sensitive values are resolved from authorized runtime services.

## 6. States

Canonical states:

```text
QUEUED
RUNNING
PAUSED
VERIFYING
UNCERTAIN
COMPLETED
FAILED
CANCELLED
```

Normal path:

`QUEUED → RUNNING → VERIFYING → COMPLETED`

Transient failure may return to `QUEUED` after retry scheduling.

`UNCERTAIN` means the executor stopped or was interrupted after durable acceptance while the external outcome cannot be proven. It is intentionally non-runnable until explicitly reconciled and requeued.

## 7. Transition Matrix

```text
QUEUED    → RUNNING | CANCELLED
RUNNING   → QUEUED | PAUSED | VERIFYING | FAILED | UNCERTAIN
PAUSED    → QUEUED | CANCELLED
VERIFYING → COMPLETED | QUEUED | FAILED | UNCERTAIN
UNCERTAIN → QUEUED (explicit reconciliation/requeue only)
COMPLETED → terminal
FAILED    → terminal unless explicit retry creates/reopens according to policy
CANCELLED → terminal
```

Every transition is validated and persisted. Illegal transitions are programming errors and must be tested.

## 8. Persistence Ordering

The critical rule is:

```text
persist intent first
        ↓
then execute
```

A command must not tell the user that durable work was accepted until the job record has committed successfully.

If persistence fails, the operation remains unaccepted from the Job Engine's perspective.

## 9. Worker Model

A worker repeatedly:

1. finds eligible jobs;
2. atomically claims one;
3. records a lease;
4. executes within resource policy;
5. renews lease while active;
6. persists progress;
7. enters verification;
8. records result;
9. releases lease.

Worker identity is process/worker scoped and unique for diagnostics.

## 10. Leases

Lease fields:

```text
worker_id
leased_at
lease_until
heartbeat_at
```

Only the current lease holder may mutate execution state.

Lease duration must exceed the expected heartbeat interval by a safe margin. Heavy work must renew while active.

## 11. Lease Expiry

An expired lease means:

```text
execution outcome = UNKNOWN
```

Recovery:

1. detect expired lease;
2. mark the job `UNCERTAIN`;
3. inspect attempt history;
4. determine whether external side effects may have occurred;
5. reconcile where possible;
6. retry only when safe;
7. explicitly requeue only after reconciliation;
8. audit the decision.

**Never automatically replay an uncertain external mutation merely because a worker disappeared.**

## 12. Retry Policy

Retries are based on stable classes:

```text
TRANSIENT
RATE_LIMITED
RESOURCE_LIMIT
TIMEOUT
INTEGRITY
INTERNAL
PERMANENT
```

Each job type defines:

```text
max_attempts
base_delay
max_delay
jitter
retryable_classes
```

There are no infinite retries.

## 13. Backoff

Conceptually:

```text
attempt 1 → base
attempt 2 → base × 2
attempt 3 → base × 4
...
cap at max_delay
apply bounded jitter
```

Provider-specific retry timing such as `Retry-After` takes precedence where appropriate.

## 14. Idempotency

Every externally mutating job declares how duplicate execution behaves.

Possible strategies:

- provider idempotency key;
- deterministic artifact key;
- check-before-create;
- reconciliation query;
- checkpoint/resume;
- safe refusal when outcome is uncertain.

Idempotency is a contract, not a generic database flag.

## 15. Verification

Verification is a first-class state.

Examples:

```text
send message
    → verify expected message/result

convert media
    → verify output exists + readable + format

backup
    → verify artifact + integrity

index
    → verify transaction/index consistency
```

A subprocess exit code of zero is evidence of executor completion, not necessarily proof of the user-visible postcondition.

## 16. Progress

Progress is informational and bounded:

```text
current
maximum
unit
message
updated_at
```

Progress must not be used as authoritative completion state.

High-frequency progress writes are throttled to avoid database contention.

## 17. Cancellation

Cancellation is persisted.

A worker should stop cooperatively at safe checkpoints. For subprocess/media work, cancellation terminates the controlled child process and cleans the workspace.

If cancellation interrupts active work, the job is `UNCERTAIN` rather than falsely terminal, because an external side effect may already have occurred. Queued work can be safely marked `CANCELLED`.

## 18. Scheduling

The scheduler selects runnable jobs using:

```text
state = QUEUED
retry_at <= now
resource class available
priority
age
plugin limits
Telegram/network limits
```

Priority does not override authorization, resource, or rate limits.

## 19. Fairness

A high-volume plugin must not starve the entire queue. The implementation may use per-plugin concurrency and simple fair selection before introducing complex scheduling algorithms.

## 20. Parent/Child Jobs

Composite workflow:

```text
BACKUP
├── PREPARE
├── COPY
├── VERIFY
└── CLEANUP
```

The parent owns intent. Children inherit bounded scope and cannot exceed parent authorization.

Parent completion requires all required child contracts to succeed.

## 21. Restart Recovery

Startup recovery inspects:

- expired leases;
- RUNNING jobs without workers;
- overdue retry times;
- VERIFYING jobs;
- UNCERTAIN jobs awaiting reconciliation;
- orphaned child jobs;
- abandoned media workspaces.

Recovery is conservative: inspect and reconcile before replaying side effects.

## 22. Resource Classes

Initial classes:

```text
LIGHT
NETWORK
MEDIA
CPU_HEAVY
AI
STORAGE
TELEGRAM
```

The current engine uses one local execution lane, which bounds total live job concurrency but does not yet expose independent per-class limits. Phase 7 must introduce explicit media/resource concurrency policy before enabling concurrent heavy media jobs.

## 23. Failure Codes

Stable codes include:

```text
INVALID_INPUT

PERMISSION_DENIED
NOT_FOUND

```

Human-readable exception strings are never the scheduler's primary classification mechanism.

## 24. Audit Events

Record material lifecycle events:

```text
CREATED
AUTHORIZED
QUEUED
LEASED
STARTED
PROGRESS
PAUSED
RETRY_SCHEDULED
VERIFYING
VERIFIED
COMPLETED
FAILED
CANCELLED
CANCELLED_UNCERTAIN
LEASE_EXPIRED_UNCERTAIN
WORKER_SHUTDOWN_UNCERTAIN
UNCERTAIN_REQUEUED
RECOVERED
```

Metadata is bounded and redacted.

## 25. Telegram Jobs

Scheduled messages, bulk actions, reminders, and automation must carry explicit scope:

```text
account
chat
message target
operation
schedule
limits
```

A scheduler must not infer broader chat/account scope from an incomplete payload.

## 26. Media Jobs

Media jobs reference source and destination artifacts rather than embedding arbitrary filesystem paths. Workspaces are job-owned.

Required cleanup states:

```text
CREATED
RUNNING
OUTPUT_READY
PROMOTED
CLEANED
ORPHANED
```

## 27. HTTP Jobs

HTTP jobs use the shared HTTP service. The job payload identifies an approved operation; it does not bypass network policy.

Retries follow HTTP semantics and never blindly replay non-idempotent mutations.

## 28. AI Jobs

AI jobs specify:

```text
provider policy
model policy
input reference
max output
resource class
```

AI results are untrusted data and require deterministic validation before becoming an external action.

## 29. Queue Backpressure

The engine must have bounded execution concurrency. Persisting a million jobs does not imply executing a million jobs concurrently.

When resources are saturated, jobs wait durably rather than consuming unbounded RAM with live tasks.

## 30. Testing Contract

Mandatory tests include:

- state transition validity;
- durable creation;
- process restart recovery;
- lease acquisition/race;
- lease expiry;
- uncertain-state recovery;
- explicit uncertain requeue;
- retry exhaustion;
- backoff bounds;
- cancellation;
- duplicate/idempotency handling;
- verification failure;
- parent/child failure;
- resource limits;
- audit emission;
- secret exclusion.

## 31. Implementation Boundary

The first implementation does **not** need distributed workers, Redis, Celery, RabbitMQ, or Kubernetes. SQLite plus a bounded local worker pool is the default.

## Final Principle

> **A job is Astra's durable memory of accepted work. It is not permission, not proof, and not a guarantee that an uncertain external side effect never happened.**
